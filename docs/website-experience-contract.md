# Clinical System｜網站閱讀體驗設計契約（Web Experience v1）

日期：2026-10-21。適用於小麻閱讀、內科國考與未來臨床專題。**這是網站產品契約，不取代 EPQC（文章品質）與 LEC（理解效率）。**

## 產品命題

網站是醫學知識的長期閱讀場域，不是研究流程儀表板、個人學習進度管理系統，也不是把各獨立網站放進同一個列表。

優先順序：

1. **內容可辨識**：讀者能從臨床問題或系列找到已公開、實際存在的文章；不把尚未回收的完稿計入文章數或填入假卡片。
2. **敘事可連續**：正文自然推進；長篇可定位，但必要機轉不藏在互動、摺疊或來源頁。
3. **互動具認知增量**：一項操作必須有助於理解因果、比較時間／空間、更新決策或檢驗反事實；若靜態文字更清楚，就不要加互動。
4. **操作成本低**：網址穩定、搜尋直接、手機可讀、不要求登入、不加第三方 UI framework。

## 資訊架構

```text
index.html（圖書館首頁）
├─ 搜尋全文、篩選已公開文章、接續閱讀（僅本機）
├─ 小麻閱讀 → 原創完整文章
├─ 小麻內科國考 → 系列入口 → 每日教材 → 閱讀路線
└─ 臨床專題 → 完整病例／機轉教材
   └─ 來源與查核（由各文頁腳或正文就地連接）
```

首頁不承載後台 metadata。文章列表只由 `site/pages.json` 的發布白名單產生；品質審查、回收進度、Agent 狀態仍在各自檔案／審查頁，而非混進閱讀動線。

## 三種頁面

**首頁（Discovery）**：一個清楚命題、一個搜尋框、已公開文章入口、兩大系列入口；具視覺層次而不會形成每篇都很大的卡片海。手機優先可用。文章數增加時可依主題作第二層索引，但不提前建立空專科分類。

**文章（Reading）**：頂欄只提供回首頁／進入系列／搜尋／閱讀設定；左側 sticky 章節進度，手機以可展開目錄代替；主要欄位以長文排版為核心。序言回答「為何要讀」，正文完整建立概念到決策，來源與版本控制不搶正文位置。

**互動理解（Teaching）**：根據主題選用 *因果條件操作*、*時間軸／影像對讀*、*反事實比較*、*決策證據更新*。互動前交代模型假設，操作後同時呈現變化、原因、未變項與限制。每種互動保留等價靜態敘述。沒有教學增量的控件不得因「豐富介面」而新增。

## 視覺原則

- 暖白／米白紙張底色、深綠文字與主色、低飽和赭色輔助；深色模式維持足夠對比。
- 標題用節制的宋體系統字型，內文以繁中易讀的系統無襯線字型，避免第三方遠端字型依賴。
- 長文避免內容變成橫跨螢幕的長行；圖表需要大於裝飾性圖片的展示空間，手機表格可水平捲動。
- 限制同屏操作數：搜尋、目錄、字體、主題優先；不要加未證實有用的徽章、浮窗、輪播或儀表板。
- 鍵盤焦點清楚，觸控目標合理，支援 `prefers-reduced-motion`，JS 關閉時正文與文章連結仍有效。

## 可量測的驗收

**工程阻擋**：既有原稿指紋不變、發布白名單與內部連結通過、每頁一個 H1、沒有私有封存檔／私人行程進公開頁。Tamponade 的 U01–U08 錨點保留在其獨立頁。

**功能驗收**：360px 與桌面實測主導航不遮擋；搜尋可以找到文章與正文詞語；分類篩選操作和 `aria-pressed` 同步；暗色模式、鍵盤焦點與接續閱讀可用；不操作也能閱讀教材。

**學習驗收（與功能不同）**：以先導主題進行高品質靜態與有認知意義互動版對照。須同時比較核心正確性、反事實遷移、完成時間、主觀負擔和回頭查找；在未實測前不得宣稱「互動讓理解快 20%」。詳見 `docs/learning-experience-contract.md`。

## 開發約束

沿用現有 Markdown → Python deterministic build → GitHub CI → Cloudflare Pages。原始內容不依賴 framework 或資料庫。先新增能直接使用的網站功能，再以實際讀者困難決定是否擴展架構。新增交互不應要求使用者維護跨主題狀態圖。

**設計的成功不是讓網站看起來更像產品，而是讓讀者更少迷路、更願意讀完，並能真正修正下一個臨床判斷。**
